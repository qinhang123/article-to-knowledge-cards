Database Index Fundamentals

Core Knowledge
A database index is a data structure that improves data retrieval speed. Without an index, the database performs a full table scan (checking every row). With an index, it can quickly locate relevant rows. The most common type is the B-tree index, which maintains sorted data and allows searches, insertions, and deletions in logarithmic time.
Explanation
An index is created on one or more columns of a table. The trade-off is faster reads at the cost of additional storage and slower writes, since the index must be maintained alongside the table data.

B-Tree Index Structure

Core Knowledge
A B-tree is a self-balancing tree that maintains sorted data. Each node can contain multiple keys and child pointers, making B-trees shallower than binary trees. The database reads data in fixed-size blocks called pages, and B-trees are designed so each node fits within a single page. The root node is always in memory, so typical lookups require only a few disk reads.
Explanation
The shallowness of B-trees means fewer disk reads because each node fits in one page and the root is always cached in memory. This is critical for large tables where disk I/O is the bottleneck.
Example
The document states that because the root node is always kept in memory, a typical lookup requires only a few disk reads even for very large tables.
Self-Test
Why does the B-tree structure result in fewer disk reads compared to a binary tree for the same number of keys?
Summary
B-trees are optimized for disk-based storage by aligning node size with page size, minimizing I/O for large datasets.

Composite Indexes and Leftmost Prefix Rule

Core Knowledge
A composite index is an index on multiple columns. The column order matters significantly: the index is sorted by the first column, then by the second within groups of the same first column value, and so on. An index on (last_name, first_name) can serve queries filtering by last_name alone or both columns, but not first_name alone. This is the leftmost prefix rule.
Explanation
The leftmost prefix rule means the index can only be used efficiently if the query filters on the leading column(s) of the composite index. Queries that skip the first column cannot leverage the index's sort order.
Example
The document gives the example of an index on (last_name, first_name): it serves queries filtering by last_name alone or both columns, but cannot efficiently serve queries filtering by first_name alone.

Index Selectivity and Optimizer Decisions

Core Knowledge
Selectivity measures how many rows an index filters out. A highly selective index leaves a small result set. A unique index has perfect selectivity. The query optimizer uses selectivity to decide whether to use an index. If an index is not selective enough, the optimizer may prefer a full table scan because the overhead of reading the index plus fetching rows exceeds a direct table scan.
Explanation
Selectivity determines the practical value of an index. An index on a low-cardinality column (e.g., gender with two values) may be ignored by the optimizer because the overhead of index lookups outweighs the benefit of filtering.
Example
The document gives the example of an index on a gender column with only two values — the optimizer may prefer a full table scan because reading the index and then fetching rows is more expensive than scanning the table directly.
Self-Test
Why might a query optimizer choose a full table scan over using an index?
Summary
Adding an index does not guarantee it will be used — the optimizer evaluates selectivity to make cost-based decisions, making index design a query-specific problem.

Covering Indexes and Index-Only Scans

Core Knowledge
A covering index contains all columns needed by a query. When available, the database satisfies the query entirely from the index without accessing table data — an index-only scan. This is significantly faster than regular index lookups because it avoids the random I/O of fetching table rows.
Explanation
Regular index lookups require two steps: find the matching index entries, then fetch the corresponding table rows. Covering indexes eliminate the second step by storing all needed columns in the index itself, avoiding expensive random disk I/O.
Example
The document gives the example of a query selecting first_name and last_name from a users table — an index on (last_name, first_name) serves as a covering index because all needed data is in the index.
Self-Test
What is an index-only scan and why is it faster than a regular index lookup?
Summary
Covering indexes are one of the most powerful query optimization techniques, eliminating random I/O at the cost of larger index sizes and more complex index maintenance.

Query Execution Plans and EXPLAIN

Core Knowledge
A query execution plan describes how the database executes a SQL statement, including which tables are accessed, which indexes are used, join methods, and estimated cost. The query optimizer generates the plan by evaluating multiple strategies and choosing the lowest-cost one. Developers use the EXPLAIN command to view the plan and identify performance issues.
Explanation
The execution plan is the optimizer's blueprint for query execution. By examining it, developers can spot missing indexes, inefficient join strategies, and other performance bottlenecks that are invisible from the SQL query alone.

Index Maintenance and Write Performance Trade-offs

Core Knowledge
Indexes improve read performance but slow down writes. Each INSERT, UPDATE, or DELETE must update all affected indexes. Over time, indexes can become fragmented due to page splits and deletions, leading to lower cache hit rates and more disk I/O. Regular index rebuilding or reorganizing restores performance. The decision to add an index should consider the read-to-write ratio, query patterns, and available storage.
Explanation
Fragmentation occurs because B-tree pages are not always full after splits and deletions. Fragmented indexes waste space and require more I/O. Rebuilding reorganizes the index to be compact and efficient again.

Full-Text Search and Inverted Indexes

Core Knowledge
Standard B-tree indexes are unsuitable for text search because they match exact values or prefixes. Full-text search uses an inverted index, which maps each word (token) to a list of documents containing it. The text is processed through tokenization (splitting into words), stemming (reducing to root forms), and stop word removal (removing common words like 'the' and 'is').
Explanation
The inverted index is fundamentally different from a B-tree: instead of mapping rows to values, it maps words to rows. Text preprocessing (tokenization, stemming, stop word removal) normalizes the text so that searches match conceptually related terms, not just exact strings.
