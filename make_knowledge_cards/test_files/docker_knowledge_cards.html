Container vs Virtual Machine

Core Knowledge
A container is a lightweight, standalone executable package that includes code, runtime, libraries, and settings. Containers share the host OS kernel rather than running a full guest OS, making them tens of megabytes versus gigabytes for VMs, and starting in seconds rather than minutes.
Explanation
Containers isolate applications from each other and the underlying infrastructure. The key difference from VMs is that containers do not bundle a full operating system, which dramatically reduces size and startup time while ensuring consistent behavior across environments.

Container Images and Registries

Core Knowledge
A container image is a read-only template built from a Dockerfile. Images are stored in registries, with Docker Hub as the default public registry. An image is referenced by name and tag (e.g., nginx:1.21), defaulting to 'latest' when no tag is specified.
Explanation
The Dockerfile contains instructions that define the image. Organizations can run private registries for internal use. Tags allow version management, with the implicit 'latest' tag being the default when none is specified.

Layered Filesystem and Copy-on-Write

Core Knowledge
Docker images use a layered filesystem based on Union File System. Each Dockerfile instruction creates a new layer. Layers are stacked and shared across images. When a container starts, a thin writable layer is added on top. Copy-on-write means modified files are copied to the writable layer before modification.
Explanation
The layered approach allows shared base layers to be stored once on disk, saving space and reducing build time. Copy-on-write preserves the original read-only layers while allowing containers to modify files without affecting the base image or other containers.
Example
The document explains that if two images share the same base layers, they share the same files on disk, saving storage space and reducing build time.
Self-Test
How does Docker's copy-on-write mechanism protect the original image when a container modifies a file?
Summary
Layered filesystems with copy-on-write enable efficient storage sharing and immutability of base images, at the cost of a small overhead when files are first modified.

Docker Client-Server Architecture

Core Knowledge
Docker uses a client-server architecture. The Docker client (docker CLI) communicates with the Docker daemon (dockerd) via a REST API. The daemon is responsible for building, running, and managing containers, and interacts with the kernel to manage container processes.
Explanation
The daemon runs on the host OS and handles all container operations. The client can connect to either a local or remote daemon, with communication happening over Unix sockets or TCP. This separation allows remote management of Docker hosts.

Container Network Drivers

Core Knowledge
Docker provides several network drivers: bridge (default, internal network on host), host (no isolation, uses host networking), none (all networking disabled), and overlay (VXLAN-based virtual network spanning multiple hosts). Port mapping exposes container ports to the host.
Explanation
Bridge networks let containers on the same bridge communicate via IP. Host networking removes isolation for maximum performance. Overlay networks enable multi-host communication. Port mapping (e.g., -p 8080:80) makes containerized applications accessible externally.
Example
The document gives the example: `docker run -p 8080:80 nginx` maps port 80 in the container to port 8080 on the host.
Self-Test

Summary
Docker's networking model offers a spectrum from full isolation (bridge) to no isolation (host), with overlay networks bridging the gap for distributed deployments.

Data Volumes and Persistence

Core Knowledge
Containers are ephemeral; their writable layer is removed when the container is removed. Docker volumes persist data beyond the container lifecycle. Volumes are managed by Docker, independent of container lifecycle, and can be shared between containers. Bind mounts mount host directories into containers but are less portable.
Explanation
Volumes are the recommended approach for data persistence because they are managed by Docker and stored in a specific location on the host. Bind mounts are more flexible but less portable. Both mechanisms prevent data loss when containers are removed.
Example
The document explains that volumes can be shared between containers and are stored in a specific location on the host, while bind mounts allow mounting any directory but are less portable.
Self-Test
What is the difference between Docker volumes and bind mounts in terms of portability?
Summary
Volumes solve the fundamental tension between container ephemerality and data persistence, with the trade-off between Docker-managed volumes and flexible bind mounts.

Docker Compose for Multi-Container Apps

Core Knowledge
Docker Compose defines and runs multi-container applications using a YAML file (docker-compose.yml). It configures all services, networks, and volumes. A single command (docker compose up) starts the entire application stack with proper networking and dependency management.
Explanation
Compose is particularly useful for development and testing. It allows defining multiple services (e.g., web server, app server, database) that need to run together, with proper networking and dependency management configured declaratively.

Container Orchestration Fundamentals

Core Knowledge
Container orchestration automates deployment, scaling, and management of containerized applications. Kubernetes is the most popular platform. Orchestration handles scheduling (which host runs which container), scaling (adding/removing instances), self-healing (restarting failed containers), rolling updates, service discovery, load balancing, and configuration management.
Explanation
As container count grows, manual management becomes impractical. Orchestration tools provide the automation needed for production deployments, ensuring high availability, efficient resource utilization, and zero-downtime updates across a cluster of machines.
